# Email provider selection for booking access codes

**Research date:** 2026-10-27
**Scope:** Resend, Amazon Simple Email Service (SES), and Postmark for low-volume, one-time transactional email from this Go backend. Prices and account rules can change; recheck the linked provider pages before signup or deployment.

## Recommendation

Use **Resend** for the first email adapter, provided we can configure DNS for a domain we control. It has an official Go SDK and a relatively small integration surface. Its current free plan allows 3,000 transactional emails per month with a global 100-per-day cap; the first paid tier is $20/month for 50,000 emails. Treat the free tier as an early pilot limit, not an assumed production capacity. [Resend pricing](https://resend.com/pricing), [Resend Go integration](https://resend.com/go), [official Go SDK](https://github.com/resend/resend-go)

This is a fit for the expected low volume, not a claim that Resend has the lowest possible per-message cost. At this volume, the price difference between providers is negligible; account onboarding and operational complexity matter more. We still need a verified sender domain for production and must configure the DNS records Resend supplies. Resend's `resend.dev` test domain is not the production sender identity. [Resend domain verification overview](https://resend.com/changelog/domain-verification-events), [Resend testing-domain guidance](https://resend.com/changelog/improved-logs-visibility)

## Why Resend wins here

The code-message workload is transactional, low-volume, and already behind a narrow sender interface. Resend lets us implement that adapter with its official Go SDK, while its free monthly allowance is more than enough for development and an early rollout. Resend also documents a 24-hour idempotency window for email sends, which is useful if the sender has to retry after an uncertain network result; the application still needs stable per-challenge idempotency keys and must not treat provider acceptance as proof of inbox delivery. [Go SDK](https://github.com/resend/resend-go), [idempotency behavior](https://resend.com/docs/dashboard/emails/idempotency-keys)

SES may be cheaper in raw unit price, but its region-specific sandbox and production review are friction without meaningful savings at the expected volume. Postmark is also technically viable over HTTP, but its 100-message free tier and $15 minimum paid tier are a worse cost fit for a small service.

## Conditions and caveats

- **Domain access is the practical prerequisite.** We need to control DNS for the sender domain and add the authentication records selected by the provider. Resend is recommended only if that is available.
- **Provider acceptance is not inbox delivery.** The access-code service should persist its challenge and attempt state safely, use a delivery timeout, log provider message IDs without logging the code, and keep the code valid only for the previously agreed 10 minutes. A send timeout can be ambiguous; retrying the exact same email should reuse a stable provider idempotency key where supported.
- **Do not put provider SDK types in the booking contract.** Keep the existing narrow email-sender interface and put the Resend client behind an adapter. That keeps a future provider switch localized.
- **Recheck limits before launch.** Resend's 100/day free cap is global to the plan, not per booking or IP. Configure provider-side billing/alerts or move to Pro before expected daily demand can exceed it.

## Decision

Adopt Resend for the first implementation, conditional on having a domain whose DNS we can manage. If that domain is unavailable, settle domain ownership before production delivery; do not build production sending around a provider's test sender.
