# Kenya online payment options for the cinema backend

**Research checked:** 7 October 2026

**Purpose:** Shortlist alternatives to a direct Safaricom Daraja integration for a Kenya-based independent cinema accepting online ticket payments. This is a technical screening, not a commercial recommendation or proof of live service quality.

## Verdict

The practical shortlist is **Paystack, Tingg (Cellulant), IntaSend, Pesapal, and Flutterwave**. All publish HTTP APIs and sandbox or test paths, so Go can integrate using `net/http` without a provider SDK. The clearest Kenya-specific breadth in the sources checked is Paystack and Tingg: both document M-Pesa alongside at least one other mobile-money rail, plus card payments. IntaSend, Pesapal, and Flutterwave are also viable candidates, with distinct trade-offs around sandbox routing, status verification, and public operational evidence.

An aggregator is an alternative integration and merchant relationship, but it does not automatically create an independent M-Pesa network path. IntaSend explicitly says its M-Pesa sandbox uses the M-Pesa developer platform. Flutterwave's status page has described a Kenya KES disruption as involving an “affected service provider.” The public sources reviewed do not establish the precise live route used by each aggregator, so ask each provider which upstream processor handles M-Pesa and what failover exists. If M-Pesa itself is unavailable, the meaningful fallback is another enabled method such as card or bank transfer, not another wrapper around the same M-Pesa rail.

**Project decision (7 October 2026):** Paystack is selected for the first provider integration, and the first release must offer both M-Pesa and cards, subject to confirming merchant eligibility and validating both methods in its current Kenya sandbox. This is a project choice, not a finding that Paystack is the most reliable provider. Its documentation offers Kenya M-Pesa test data, card tests, Airtel Money, signed webhooks, retries, and transaction verification. A local deterministic fake provider should still be used to exercise edge cases that the sandbox cannot reliably produce. Direct Daraja production verification is deferred because the cinema is fictional and has no live shortcode. Safaricom's Go Live guidance requires a live Paybill/Till shortcode and organization admin/manager details; its C2B simulator is sandbox-only. [Safaricom C2B documentation](https://developer.safaricom.co.ke/apis/CustomerToBusiness) · [Daraja getting started](https://developer.safaricom.co.ke/apis/GettingStarted). No production payment testing is planned for this learning project.

## What this means for reliability

1. **Separate seat reservation from payment truth.** Keep a booking in `PAYMENT_PENDING` while the provider has not confirmed the exact amount, currency, reference, and successful state. A redirect or client callback is not proof of payment.
2. **Expect ambiguous outcomes.** A network timeout after creating a charge does not tell the application whether the provider accepted it. Persist an internal payment attempt and reference before the provider call; reconcile using the provider lookup API or dashboard before starting a second charge.
3. **Make inbound events idempotent.** Record provider event or transaction IDs, enforce uniqueness in the database, and make state transitions safe to repeat. Keep polling/reconciliation for pending attempts because webhook delivery can fail or arrive late.
4. **Avoid overstating provider idempotency.** None of the reviewed public collection docs provided a clear universal idempotency-key guarantee for creating a customer payment. A merchant reference is useful for correlation, but is not by itself proof that retrying a create request cannot produce another charge.
5. **Plan real failover intentionally.** M-Pesa through different PSPs may still depend on the same Safaricom service. Cards/PesaLink can provide a different payment method, but that is only useful if the cinema accepts the customer experience, fees, settlement delay, and reconciliation implications.

## Onboarding questions before choosing

Ask each provider to answer in writing:

- Can a newly onboarded Kenyan cinema business accept KES M-Pesa STK and card payments? What business documents, website, settlement account, minimum volume, and review period are required?
- Which M-Pesa upstream route is used in production? Is it Daraja, another Safaricom channel, or a licensed partner? What failover occurs if that route is degraded?
- Is there a merchant-facing or contractual uptime/availability target for collections, and does it cover the upstream mobile-money network?
- What are the fees, settlement timing, refund/void rules, chargeback workflow, transaction limits, and support escalation hours?
- Can we obtain test scenarios for delayed/pending, duplicate callback, callback retry, late success after timeout, partial outage, and reversal?
- What are the exact idempotency semantics for charge creation? If none, what lookup key safely resolves an uncertain create request?
- Can we use sandbox credentials without a fully approved live merchant account, and what differs between sandbox and production?

## Recommendation for the brief

Keep **Paystack M-Pesa and card checkout** as the first provider integration, subject to merchant eligibility and sandbox validation of both methods. Implement a small `PaymentProvider` boundary and keep booking/payment state transitions provider-neutral. A deterministic fake provider should be used for repeatable timeout, duplicate, delayed, and out-of-order event scenarios; it does not replace Paystack sandbox validation. Add another live provider only if an explicit customer requirement justifies the added reconciliation and operational surface. Direct production Daraja remains unverified until there is legitimate merchant shortcode access.

For this cinema, a defensible initial acceptance rule is: **a seat is confirmed and its ticket is issued only after a verified successful payment for the expected booking; pending or ambiguous payments keep the booking recoverable and do not trigger a second charge automatically.** The agreed initial seat hold is five minutes. If payment is still ambiguous at expiry, retain the seat. If automatic reconciliation cannot resolve it, flag it for staff review and continue reserving the seat until staff act; the authorized staff actions remain to be defined.

## Evidence limits

- This report uses provider-owned developer, support, and status pages. Those sources establish what vendors document and publish; they do not independently establish transaction success rates, peak-load performance, dispute outcomes, real-world webhook delivery, or end-to-end uptime.
- Status pages are self-reported and often report API/platform components rather than the complete chain from checkout through mobile operator and settlement. A green status indicator is not proof that a test payment will succeed.
- Sandbox behavior is not proof of production behavior. IntaSend explicitly routes its documented sandbox M-Pesa test through the M-Pesa developer platform; confirm production routing and limitations directly with the provider.
- This is not legal, tax, PCI, or commercial due diligence. Confirm live merchant terms, applicable Kenyan regulatory requirements, pricing, data handling, and settlement arrangements before production.
- Current product and API behavior can change. Recheck the provider's official docs and account dashboard during implementation; Flutterwave especially has distinct v3 and v4 webhook guidance.
